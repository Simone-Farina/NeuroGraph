## Summary

This phase adds a transient visual feedback layer to the chat: after the Bloom evaluator classifies a user's message, the specific key phrases that drove that classification are highlighted with a soft background tint in the corresponding Bloom level color, fade in over 300ms, remain visible for 5 seconds, then fade out. The feature requires changes in four files: the evaluator API route (schema + prompt), the Zustand store (new state field), the ChatPanel (response parsing), and MessageList (highlight rendering).

The core technical problem is inline text highlighting in React — splitting raw text strings around matched substrings and wrapping matched spans in styled elements. This is a solved but moderately fiddly problem: the naive approach breaks on regex special characters, overlapping matches, and case sensitivity. Using a simple split-on-matches algorithm (case-insensitive, exact substring match) is the correct level of complexity for this use case. Framer Motion v12.34.0 is already installed and used throughout the project (`motion`, `AnimatePresence`); it is the idiomatic choice for the fade-in entrance. The 5-second auto-fade-out is cleanly handled with a `useEffect` cleanup `setTimeout`.

The Bloom evaluator already returns JSON. Adding `key_phrases: string[]` to the schema is a minimal extension — one new field in the prompt output format instruction and one new validation path in the response parser. No model change is required; the existing `evaluator` role model handles it.

**Primary recommendation:** Implement inline highlighting in `MessageList.tsx` using a pure React split-based approach (no external library). Use Framer Motion's `animate` + `initial` props on highlight spans for the fade-in. Use `useEffect` with a 5-second `setTimeout` in `MessageList` (or a dedicated hook) to toggle highlights off.

### Pattern 1: Inline Text Highlighting (Split-Based)

**What:** Split the raw message text on matched key phrases and render alternating plain/highlighted spans.

**When to use:** Whenever key phrases must be highlighted inline within flowing text, without wrapping the text in a rich-text editor or markdown processor.

**Critical nuance for this codebase:** The current user message rendering in `MessageList.tsx` (line 63-76) renders `part.text` as a raw string inside a `<div>`. It does NOT use ReactMarkdown (that is only for assistant messages). This means we can safely split the string and render `<span>` elements — no need to fight a markdown renderer.

**Algorithm:**
```typescript
// Source: standard React inline highlighting pattern
function highlightText(
  text: string,
  phrases: string[],
  isHighlighted: boolean,
  highlightClass: string
): React.ReactNode {
  if (!isHighlighted || phrases.length === 0) return text;

  // Build a single regex from all phrases (case-insensitive, escaped)
  const escaped = phrases.map((p) =>
    p.replace(/[.*+?^${}()|[\]\\]/g, '\\$&')
  );
  const pattern = new RegExp(`(${escaped.join('|')})`, 'gi');
  const parts = text.split(pattern);

  return parts.map((part, i) => {
    const isMatch = pattern.test(part);
    pattern.lastIndex = 0; // reset stateful regex after test()
    if (isMatch) {
      return (
        <motion.span
          key={i}
          initial={{ backgroundColor: 'transparent' }}
          animate={isHighlighted ? { backgroundColor: 'var(--highlight-color)' } : { backgroundColor: 'transparent' }}
          transition={{ duration: 0.3 }}
          className="rounded-sm"
        >
          {part}
        </motion.span>
      );
    }
    return <span key={i}>{part}</span>;
  });
}
```

**Simpler Tailwind-only alternative (recommended given D-10's explicit `transition-colors duration-300` directive):**
```typescript
// Tailwind className toggle via state — no Framer Motion needed for this specific case
// Each matched span gets className toggled between '' and highlightClass
// React re-render triggers Tailwind transition-colors duration-300
<span
  className={`rounded-sm transition-colors duration-300 ${
    isHighlighted ? highlightClass : ''
  }`}
>
  {part}
</span>
```

The Tailwind className-toggle approach is recommended over Framer Motion `animate` for this specific animation because:
1. D-10 explicitly calls out `transition-colors duration-300` as the pattern to follow
2. Background color transitions work cleanly with Tailwind's `transition-colors`
3. Less complexity — no `motion.span` overhead on every text part

### Pattern 3: Auto-Fade-Out Timer (5-Second Ephemeral Highlight)

**What:** Trigger a state change 5 seconds after highlights appear, transitioning them back to transparent.

**Implementation in MessageList:** Subscribe to `bloomKeyPhrases` from Zustand. When it becomes non-empty, start a `setTimeout(5000)`. On timeout, call a local state setter `setIsHighlighted(false)`. The `isHighlighted` boolean gates the highlight class on each span. When the Bloom eval resets (new conversation), `bloomKeyPhrases` becomes `[]` which also clears highlights.

```typescript
// In MessageList (or a dedicated hook useBoomHighlight):
const bloomKeyPhrases = useGraphStore((s) => s.bloomKeyPhrases);
const latestBloomMessageId = useGraphStore((s) => s.latestBloomMessageId);
const [isHighlighted, setIsHighlighted] = useState(false);

useEffect(() => {
  if (bloomKeyPhrases.length === 0) {
    setIsHighlighted(false);
    return;
  }
  setIsHighlighted(true);
  const timer = setTimeout(() => setIsHighlighted(false), 5000);
  return () => clearTimeout(timer);
}, [bloomKeyPhrases]);
```

**Note:** `isHighlighted` must be local component state (not Zustand) because it represents a transient UI animation state that should not persist across renders or affect other components.

### Pattern 4: Identifying the "Latest User Message"

**What:** Determine which message to highlight. D-07 says only the most recent user message.

**Challenge:** The Bloom eval fires async (after the assistant responds). By the time results arrive, there are at least 2 messages: the user's and the assistant's. The "latest user message" is the last message in the `messages` array with `role === 'user'`.

**Approaches:**
1. **Store the message ID** at the time `triggerBloomEval` fires (RECOMMENDED). In `triggerBloomEval`, after extracting `last6`, get `messagesRef.current.filter(m => m.role === 'user').at(-1)?.id` and pass it to `setBloomEval`. Then in `MessageList`, only render highlights on the message whose `id` matches `latestBloomMessageId`.
2. **Derive at render time** — filter `messages` for `role === 'user'` and `messages.at(-1)`. This works but could theoretically pick the wrong message if a new message arrives between eval fire and result receipt.

Option 1 (storing message ID at trigger time) is more robust and is the recommended approach.

### Anti-Patterns to Avoid

- **DOM manipulation for highlighting:** Never use `.innerHTML` replacement or `document.querySelector` to inject highlight spans. React owns the DOM — use state-driven rendering only.
- **Global timer in Zustand:** Do not put the 5-second timer in the store. Timers in Zustand actions are invisible to React's lifecycle and create memory leaks on unmount. Keep the timer in a component-level `useEffect`.
- **Highlighting assistant messages:** D-09 is explicit — assistant messages use ReactMarkdown and should never be highlighted. The split-based approach is only applied to `message.role === 'user'` parts.
- **Greedy regex without escaping:** Raw `key_phrases` strings from the LLM may contain regex metacharacters (parentheses, dots, etc.). Always escape phrases before building a regex: `phrase.replace(/[.*+?^${}()|[\]\\]/g, '\\$&')`.
- **Not resetting `pattern.lastIndex`:** When using a stateful regex with the `g` flag, `pattern.test()` advances `lastIndex`. Always reset to 0 after each `test()` call or use `match()` instead.
- **Animating layout properties:** Per the animate skill — never animate `width`, `height`, `padding`. Only animate `opacity` or `background-color` (via Tailwind `transition-colors`).

## Common Pitfalls

### Pitfall 1: Regex `lastIndex` Drift

**What goes wrong:** Split regex built with `gi` flags retains state between calls. `pattern.test(part)` after `text.split(pattern)` will produce inconsistent `true`/`false` results because `lastIndex` is non-zero after the split.

**Why it happens:** JavaScript regex objects with `g`/`y` flags maintain `lastIndex` across calls.

**How to avoid:** Reset after each `.test()` call: `pattern.lastIndex = 0`. Or use `new RegExp(...)` inside the map callback (fresh instance). Or restructure to avoid `.test()` entirely — use index-based detection via the split position.

**Warning signs:** Alternating correct/incorrect highlight detection. Odd-indexed parts match, even-indexed don't.

### Pitfall 2: The Latest Message ID Race Condition

**What goes wrong:** The user sends message A, triggers Bloom eval. Before the eval returns, the user sends message B and gets a response. The Bloom eval for message A arrives and highlights message B (the new "last user message").

**Why it happens:** Deriving "latest user message" at render time rather than at trigger time.

**How to avoid:** Capture and store the message ID at `triggerBloomEval` call time (when `last6` is built). Pass to `setBloomEval` alongside `key_phrases`. Check `message.id === latestBloomMessageId` in MessageList before rendering highlights.

**Warning signs:** Highlights appear on the wrong message when the user types quickly.

### Pitfall 3: Highlights Persisting Across Conversation Switches

**What goes wrong:** User switches conversation. The old `bloomKeyPhrases` and `latestBloomMessageId` still sit in Zustand. The new conversation shows highlights on its last user message (wrong).

**Why it happens:** `resetBloomEval` is called in `ChatPanel.tsx` `useEffect` on `currentConversationId` change (line 215), but if `bloomKeyPhrases` is not included in the reset, highlights persist.

**How to avoid:** Confirm `resetBloomEval` clears `bloomKeyPhrases: []` and `latestBloomMessageId: null` — not just `bloomLevel` and `bloomConfidence`.

**Warning signs:** Opening an existing conversation briefly shows highlights that weren't there before.

### Pitfall 4: Empty `key_phrases` When LLM Doesn't Comply

**What goes wrong:** The LLM occasionally returns the JSON without a `key_phrases` field (e.g., during degradation, when the prompt is slightly reformatted, or with older model behavior).

**Why it happens:** The evaluator prompt instructs the model to return JSON. If the model omits `key_phrases`, the current parser's type guard will pass (since it only checks `bloom_level`, `confidence`, `reasoning`) but `key_phrases` will be `undefined`.

**How to avoid:** In the API route's JSON parser, add: `key_phrases: Array.isArray((result as any).key_phrases) ? (result as any).key_phrases as string[] : []`. Default to empty array, never throw. In `triggerBloomEval`, pass `result.key_phrases ?? []` to `setBloomEval`.

**Warning signs:** `TypeError: Cannot read properties of undefined (reading 'map')` in MessageList.

### Pitfall 5: Case Sensitivity Mismatch Between LLM Output and Message Text

**What goes wrong:** LLM returns `"Compared Tradeoffs"` (title-cased), user typed `"compared tradeoffs"` (lowercase). Exact match fails, nothing highlights.

**Why it happens:** The LLM may normalize or rephrase extracted phrases slightly.

**How to avoid:** Use case-insensitive regex matching (`gi` flag). The match finds the phrase regardless of casing, and the highlight wraps the original text (not the LLM version).

### MessageList Highlight Rendering

```typescript
// Source: pattern derived from project conventions + standard React inline highlighting
// Add to top of MessageList.tsx (or extract to useBoomHighlight hook):

function useBloomHighlight() {
  const bloomKeyPhrases = useGraphStore((s) => s.bloomKeyPhrases);
  const latestBloomMessageId = useGraphStore((s) => s.latestBloomMessageId);
  const bloomLevel = useGraphStore((s) => s.bloomLevel);
  const [isHighlighted, setIsHighlighted] = useState(false);

  useEffect(() => {
    if (bloomKeyPhrases.length === 0) {
      setIsHighlighted(false);
      return;
    }
    setIsHighlighted(true);
    const timer = setTimeout(() => setIsHighlighted(false), 5000);
    return () => clearTimeout(timer);
  }, [bloomKeyPhrases]);

  return { isHighlighted, bloomKeyPhrases, latestBloomMessageId, bloomLevel };
}

function renderHighlightedText(
  text: string,
  phrases: string[],
  isHighlighted: boolean,
  highlightClass: string
): React.ReactNode {
  if (!isHighlighted || phrases.length === 0) return text;

  const escaped = phrases.map((p) => p.replace(/[.*+?^${}()|[\]\\]/g, '\\$&'));
  const pattern = new RegExp(`(${escaped.join('|')})`, 'gi');
  const parts = text.split(pattern);

  return parts.map((part, i) => {
    // Odd-indexed parts from split(captureGroup) are the matched phrases
    const isMatch = i % 2 === 1;
    return isMatch ? (
      <span
        key={i}
        className={`rounded-sm transition-colors duration-300 ${highlightClass}`}
      >
        {part}
      </span>
    ) : (
      <span key={i}>{part}</span>
    );
  });
}
```

**Note on the split pattern:** When using `String.split()` with a **capturing group** regex (i.e., `/(pattern)/`), JavaScript includes the matched captures in the result array at odd indices. This is more reliable than using `pattern.test()` in a subsequent map — it avoids the `lastIndex` pitfall entirely.

```
"X because the bottleneck matters".split(/(because the bottleneck)/gi)
→ ["X ", "because the bottleneck", " matters"]
//  [0]     [1] — match            [2]
```

Odd index `[1]` is the highlighted part. No `.test()` call needed.

## Open Questions

1. **`key_phrases` precision vs. verbosity**
   - What we know: D-01 says the LLM returns phrases it "considered for classification." These may be slightly paraphrased rather than verbatim substrings.
   - What's unclear: If the model returns a paraphrased phrase that doesn't exist verbatim in the message, the split-based matcher will find 0 matches and render no highlights.
   - Recommendation: The prompt (D-02) should explicitly instruct the model to return verbatim substrings. Add to the prompt: "Extract phrases verbatim from the user messages — do not paraphrase or normalize." If case-insensitive matching still finds no match, fail silently (no highlight) rather than showing incorrect highlights.

2. **Opacity value `/10` vs `/15` for background tint**
   - What we know: The chat panel background is `neural-gray-900/30` (very dark). At `/10` opacity, warm colors like amber and orange will be nearly invisible.
   - What's unclear: The exact RGB value of `bg-amber-400/10` against `#111111` background has not been visually tested.
   - Recommendation: Start with `/15` for the warmer colors (Analyze, Evaluate, Create) and `/10` for the cooler colors (Remember, Understand, Apply). This is within Claude's Discretion.

3. **Promptfoo eval runner availability**
   - What we know: `prompt-eval/bloom-evaluator/promptfooconfig.yaml` exists. The provider is `exec:node ../shared/neurograph-bloom-evaluator-provider.mjs`.
